# Agent instructions

Two runbooks follow: setting up a new owner's instance, and upgrading an existing instance to live provider sessions. In both, inspect before changing, reuse working authorization, and never print secrets, environment dumps, `.env` files, sealed values or provider session files. Report resource identities and remaining prerequisites, never secret values.

## Set up a new owner's instance

When asked to install or deploy this project, follow [Deploy your own](docs/deploy-your-own.md) in order. The objective is an independent deployment with the owner's own database, Vercel project, worker and provider accounts. Do not reuse the original author's service, tailnet, paths or credentials.

1. Inspect the checkout, tool versions, running services and existing configuration before changing them. Reuse working authorization and bindings. Inspect credential names/presence only.
2. Clarify only missing functional requirements: demo versus real subscriptions; which providers/repositories; an existing persistent worker versus a new machine. Default to a dedicated Vercel service and persistent worker if the owner asked for that. Owner hosting access and provider approvals remain prerequisites.
3. Prepare Node 22, pnpm 11.19.0 and PostgreSQL. Use `pnpm install --frozen-lockfile`. Work in the current checkout; do not create a Git worktree solely for setup.
4. Provision the owner's database and obtain its binding through protected secret settings. Use `pnpm setup:init --directory PRIVATE_DIRECTORY --worker-id worker-1` to generate independent role secrets, including the web role's `LLM_SESSION_KEY`. The directory must be outside the checkout and new. Existing injected role secrets are reused; existing setup directories are preserved. If the database is not yet configured, the helper reports that explicitly. It does not deploy or connect accounts.
5. Configure a new Vercel project rooted at `apps/web`, using only the generated web-role variables (`DATABASE_URL`, `LLM_SESSION_KEY`, `DASHBOARD_PASSWORD`, `READ_TOKEN`, `WRITE_TOKEN`, `JOB_TOKEN`, `ADMIN_TOKEN`, `WORKER_<ID>_TOKEN`). Use an authenticated hosting tool to set values without displaying them. If no hosting tool is available, prepare the configuration and direct the owner to [the Vercel import page](https://vercel.com/new); never ask for a token in chat. Migrate the destination database before validating the deployment. Do not seed mock accounts into production.
6. Install the official provider CLIs manually or use the optional `ai-builder-tools` setup pack. Create persistent auth/artifact directories and a version-1 tools manifest; run `collector/bin/init-worker.mjs` with the owner's service URL, machine ID and allowed repository paths. Keep at least one target and remove providers the owner did not request. Multiple machines using the same real account should retain its stable account ID, so central leases apply.
7. Register the worker's accounts and targets with temporary operator/admin access (`pnpm --filter @llm-usage/collector register CONFIG`). Registration creates the account rows that `/connect` lists.
8. Have the owner connect each provider once at the deployed dashboard's `/connect` page (dashboard sign-in first). The owner completes the provider's own sign-in in their browser and pastes back what it shows; the service stores the grant sealed with `LLM_SESSION_KEY`, reads usage from it live and issues access tokens to workers. Do not run CLI logins on the worker, request passwords/codes/OAuth tokens in chat, or copy login state between machines. Anthropic/OpenAI/Cursor API keys are unnecessary for subscription execution. Do not silently substitute separately billed API access.
9. Confirm subscription allowance and overage settings before marking a target `billing: subscription`; re-register after changing it. Check that the dashboard shows **Live** and real percentages/reset dates for each connected account (or `GET /v1/status` with `READ_TOKEN`), then start one supervised worker with only its worker secret. Do not make interactive login part of automatic startup; the worker has none.
10. Configure the owner's MCP client with the service's `/mcp` URL and JOB_TOKEN through client secret settings. Use bearer-header-compatible Streamable HTTP; OAuth discovery is not implemented.
11. Verify actual deployment access, live quota compared against each provider's own usage screen, a task producing the expected patch, and a second task after an idle worker restart. Installed binaries, generated files, fixture tests and a successful Vercel build do not prove live provider readiness.

Use `pnpm setup:run --file PRIVATE_ROLE_JSON -- COMMAND [ARGS]` when running migration, registration, client or worker commands with generated role files. This wrapper excludes unrelated inherited credentials. Load the appropriate role; never source the service's entire environment into a worker. Keep private files outside Git and provide only necessary project credentials through a separate project-specific process.

## Upgrade an existing instance to live provider sessions

Use this when an instance predates service-held provider sessions (it has a worker or scheduled job publishing usage to `/v1/ingest`, a `usage_mirror` block, `usage:sync`, or a phone-link Claude login). The outcome: the service reads usage live from its own grants, every publisher is retired, and the worker fetches access tokens instead of logging in.

1. **Inventory, read-only.** Find every process or schedule that posts usage: `crontab -l` (user and root), `/etc/cron.d`, `systemctl list-timers --all`, `systemctl --user list-timers --all`, launchd agents on Macs (`launchctl list | grep -i -E 'llm|usage|sync'`), and any `usage:sync`/`mock-sync` loops. Note which checkout and which secret source each uses. Report the list before stopping anything.
2. **Service first.** Add `LLM_SESSION_KEY` (64 hex characters, `openssl rand -hex 32`) to the web service's protected environment; the owner can set it in the hosting dashboard if the agent's tool lacks permission to create production variables. Deploy the release that contains `/connect`. The `provider_sessions` table is created on first use; running `pnpm db:migrate` with the operator role is equivalent. Pushed usage now receives `410`, so existing publishers stop overwriting readings without being touched.
3. **Owner connects providers.** Direct the owner to `https://THEIR_DASHBOARD/connect` after dashboard sign-in. Account IDs there must match the worker's `account_id` values; registration already created them. Each card should read **Live**. If one reads **Sign in again** or shows a diagnostic, report it verbatim; do not work around it with CLI logins or copied tokens.
4. **Worker.** With the worker idle, stop it; update its checkout to the release; `pnpm install --frozen-lockfile`; leave `worker.json`'s `service_url`, targets and `auth_dir`s as they are (a leftover `usage_mirror` block is ignored with a warning and can be removed). Start it. Expected log line: access tokens are issued by the service. `needs_login` for an account means it is not connected at `/connect`, not that a CLI login is required.
5. **Retire publishers.** Only after step 3 shows **Live**, disable the scheduled jobs found in step 1 (`launchctl bootout gui/$(id -u)/LABEL` and delete the plist on Macs; `crontab -e`/`systemctl --user disable --now TIMER` on Linux) and remove `LLM_USAGE_WRITE_TOKEN`/`WORKER_DASHBOARD_WRITE_TOKEN` from their secret sources. Confirm in the service's request logs that only the live reads remain.
6. **Verify.** Compare the dashboard's percentages and reset dates against each provider's usage screen; call MCP `list_accounts` and confirm each account's `observations` outcome is `observed` or `cached`; run one small task and one task after an idle worker restart.

Ask the owner only for what cannot be inspected: hosting-tool permission, the provider sign-ins, and the decision to disable a publisher the inventory could not attribute.

## Code and validation

Keep provider telemetry, enrollment and credential-file code in `packages/providers`, and CLI execution adapters in `collector/src/providers/<provider>`.
Provider grants are persisted only sealed with `LLM_SESSION_KEY`; never persist plaintext credentials, HTML, or PKCE state in the database, and never return refresh tokens from any API. Timestamps stay UTC in the API.
Add tests when modifying reset semantics, routing decisions, enrollment flows, or the public `/v1` contract.
Use feature branches and small commits; keep secrets and browser profiles out of Git.

Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` for application changes. Setup helper tests are included in `pnpm test`. Use the opt-in PostgreSQL lifecycle suite for queue/store changes with a disposable database; follow the commands in the getting-started guide. For documentation-only edits, check links and affected command examples instead of rerunning unrelated suites.
