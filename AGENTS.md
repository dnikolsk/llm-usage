# Agent instructions

Two runbooks follow: setting up a new owner's instance, and upgrading an existing instance to live provider sessions. In both, inspect before changing, reuse working authorization, and never print secrets, environment dumps, `.env` files, sealed values or provider session files. Report resource identities and remaining prerequisites, never secret values.

## Set up a new owner's instance

When asked to install or deploy this project, follow [Deploy your own](docs/deploy-your-own.md) in order. The objective is an independent deployment with the owner's own database, Vercel project, provider accounts and optional coding worker. Do not reuse the original author's service, tailnet, paths or credentials.

1. Inspect the checkout, deployed revision, tool versions and existing secret bindings before changing them. Reuse working authorization; inspect credential names/presence only. Never assume an old command exists: check `package.json` and the current runbook first.
2. Clarify only missing functional requirements: dashboard only or coding tasks, requested providers/repositories, and an existing persistent worker versus a new host. A Vercel dashboard can read usage without a worker. Default to the owner's own Vercel project and PostgreSQL database; add a persistent worker for coding tasks.
3. Use the existing checkout (no worktree solely for setup), Node 22, pnpm 11.19.0 and `pnpm install --frozen-lockfile`. Keep generated secrets outside Git. Do not seed mock accounts into production.
4. Follow [the hosted setup walkthrough](docs/deploy-your-own.md) for resource creation, `pnpm setup:init`, role-file bindings, migration and deployment. The private output directory must be new and outside the checkout. The helper does not deploy or connect providers. If `database_configured` is false, securely bind `DATABASE_URL` in both web/operator roles before migrating.
5. Configure the Vercel root as `apps/web` and Node 22.x. Bind the web role's `variables` as separate server-side settings. Preserve `LLM_SESSION_KEY` during upgrades; back it up securely. Run `pnpm db:migrate` with the operator role and deploy/redeploy. Verify actual dashboard sign-in and database access, not only a successful build. Use authorized hosting tools when available; otherwise direct the owner to Vercel's protected settings without requesting secret values in chat.
6. At `/connect`, add requested accounts or reuse existing ones. Prefer the documented default IDs for a fresh personal setup. Before registering a worker, list existing IDs via `/connect` or `GET /v1/status?fresh=0` with `READ_TOKEN`; one real provider login gets one stable ID across machines. Never create a second ID to work around a sign-in problem.
7. Have the owner connect each provider in their own browser at the hosted `/connect` page. Codes and redirect URLs go only into that page. The service stores the grant encrypted, reads usage and issues access tokens to workers. Do not run CLI logins, copy browser state or substitute separately billed API keys for the managed worker. `/connect` says **Connected**; the dashboard says **Live**. Neither proves successful telemetry: check timestamps, status, diagnostics and provider-screen values as well.
8. For coding tasks, follow [worker setup](docs/getting-started.md#connect-a-real-worker). Install official CLIs manually or use the optional companion setup pack. For a subset of providers, copy/trim the example worker config; the generator requires Claude/Codex/Cursor manifest paths and optionally adds Gemini. Keep at least one target, persistent auth/artifact paths, and allowed committed Git repositories. Use the same account IDs as step 6. Confirm included allowance/overage settings before setting `billing: subscription`; register with temporary admin access. Run one supervised worker per ID using only its worker token. Workers poll outbound HTTPS; private SSH/Tailscale access is not a prerequisite for service-side usage reads.
9. Configure the client's `/mcp` URL and JOB_TOKEN through its secret settings. Use bearer-header-compatible Streamable HTTP; OAuth discovery is not implemented. The dashboard password is not a client token.
10. Verify dashboard access and real usage for every requested provider. Then, if execution is requested, inspect plans, run a small patch-producing task, review the patch and repeat with a new job after an idle worker restart. `scripts/verify-execution.mjs --run` consumes real allowance and checks auto execution; its explicit provider plans are not proof every provider can execute. See the guide for its required positional arguments and repository flag.
11. Report deployment URL and revision, account/worker IDs, checks performed, known unsupported fields and remaining owner actions. Never report “ready” on the strength of generated files, fixture tests, a Connected badge or a Vercel build alone.

Use `pnpm setup:run --file PRIVATE_ROLE_JSON -- COMMAND [ARGS]` when running migration, registration, client or worker commands with generated role files. This wrapper excludes unrelated inherited credentials. Load the appropriate role; never source the service's entire environment into a worker. Keep private files outside Git and provide only necessary project credentials through a separate project-specific process.

## Upgrade an existing instance to live provider sessions

Use this when an instance predates service-held provider sessions (it has a worker or scheduled job publishing usage to `/v1/ingest`, a `usage_mirror` block, `usage:sync`, or a phone-link Claude login). The outcome: the service reads usage live from its own grants, every publisher is retired, and the worker fetches access tokens instead of logging in.

1. **Inventory, read-only.** Find every process or schedule that posts usage: `crontab -l` (user and root), `/etc/cron.d`, `systemctl list-timers --all`, `systemctl --user list-timers --all`, launchd agents on Macs (`launchctl list | grep -i -E 'llm|usage|sync'`), and any `usage:sync`/`mock-sync` loops. Note which checkout and which secret source each uses. Report the list before stopping anything.
2. **Service first.** Make sure the web service's protected environment has every role secret the worker and clients will use: `LLM_SESSION_KEY` (64 hex characters, `openssl rand -hex 32`), `JOB_TOKEN`, `ADMIN_TOKEN`, `READ_TOKEN`, `DASHBOARD_PASSWORD` and `WORKER_<ID>_TOKEN` for this worker's ID (hyphens to underscores, uppercase). Use existing authorized hosting access to inspect binding names and configure missing variables. If that access is unavailable, give the owner the exact variable names that are missing (a `401` from the service on registration or worker calls is the symptom) and never the values. Each added variable needs a redeploy to take effect. Deploy the release that contains `/connect`. The `provider_sessions` table is created on first use; running `pnpm db:migrate` with the operator role is equivalent. Pushed usage now receives `410`, so existing publishers stop overwriting readings without being touched.
3. **Owner connects providers.** Direct the owner to `https://THEIR_DASHBOARD/connect` after dashboard sign-in (Claude, Codex, Cursor, and Gemini if the owner uses it). Account IDs there must match the worker's `account_id` values. If the dashboard already has connected accounts under different IDs than the worker config, change the worker config to the connected IDs and re-register (target IDs stay, their account moves); do not ask the owner to sign in a second time for the same login, and remove mistaken IDs from `/connect` only once they have no session, targets or jobs. Each card should read **Connected** at `/connect` (**Live** on the dashboard). If one reads **Sign in again** or shows a diagnostic, report it verbatim; do not work around it with CLI logins or copied tokens.
4. **Worker.** With the worker idle, stop it; update its checkout to the release; `pnpm install --frozen-lockfile`; leave `worker.json`'s `service_url`, targets and `auth_dir`s as they are (a leftover `usage_mirror` block is ignored with a warning and can be removed). Start it. Expected log line: access tokens are issued by the service. `needs_login` for an account means it is not connected at `/connect`, not that a CLI login is required.
5. **Retire publishers.** Only after step 3 shows **Connected** and usage checks succeed, disable the scheduled jobs found in step 1 (`launchctl bootout gui/$(id -u)/LABEL` and delete the plist on Macs; `crontab -e`/`systemctl --user disable --now TIMER` on Linux) and remove `LLM_USAGE_WRITE_TOKEN`/`WORKER_DASHBOARD_WRITE_TOKEN` from their secret sources. Confirm in the service's request logs that only the live reads remain.
6. **Verify.** Compare the dashboard's percentages and reset dates against each provider's usage screen; call MCP `list_accounts` and check observation outcomes together with account status, freshness and diagnostics (`cached` may reuse an error); run one small task and one task after an idle worker restart.

Ask the owner only for what cannot be inspected: hosting-tool permission, the provider sign-ins, and the decision to disable a publisher the inventory could not attribute.

## Diagnose current usage before touching workers

Use [troubleshooting](docs/troubleshooting.md). `usage:doctor`, `usage:sync` and usage mirroring were removed when observation moved into the service. Do not prescribe these commands or restore a publisher to fix missing dashboard values. Real pushes to `/v1/ingest` are retired.

`GET /v1/status?fresh=0` reads stored data only; `/v1/status`, dashboard views and MCP reads may refresh grants and persist observations. Compare account IDs and deployment/database identity before comparing readings. Inspect `status`, `usage_diagnostic`, `observed_at`, `latest_refresh_at`, each bucket's `reset_at`, and `paid_usage`/`paid_usage_diagnostic`. Missing reset dates and paid amounts remain unknown. A disabled spending budget is not proof of a zero wallet balance; credits and USD must retain their reported units. Paid telemetry never authorizes spending or expands routing capacity.

## Documentation maintenance

`AGENTS.md` is the canonical agent entry point; do not create a conflicting `agent.md`. Keep [README](README.md) as the short entry, [Deploy your own](docs/deploy-your-own.md) as the ordered owner walkthrough, [Getting started](docs/getting-started.md) for local/worker commands, and the remaining docs as references. Update diagrams when credential ownership or data flow changes. Use generic owner placeholders, never personal deployments, live balances or machine paths as setup defaults.

When changing setup instructions, validate script names against package manifests, local links/anchors, shell examples, private-role generation and worker-config generation. Use disposable paths and test data for validation; never rotate an existing deployment's secrets merely to test documentation. Report local checks separately from live acceptance.

## Code and validation

Keep provider telemetry, enrollment and credential-file code in `packages/providers`, and CLI execution adapters in `collector/src/providers/<provider>`.
Provider grants are persisted only sealed with `LLM_SESSION_KEY`; never persist plaintext credentials, HTML, or PKCE state in the database, and never return refresh tokens from any API. Timestamps stay UTC in the API.
Add tests when modifying reset semantics, routing decisions, enrollment flows, or the public `/v1` contract.
Use feature branches and small commits; keep secrets and browser profiles out of Git.

Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` for application changes. Setup helper tests are included in `pnpm test`. Use the opt-in PostgreSQL lifecycle suite for queue/store changes with a disposable database; follow the commands in the getting-started guide. For documentation-only edits, check links and affected command examples instead of rerunning unrelated suites.
